# Directory drives: a proposal

Written 2026-11-01 (PIZERO-288) from a discussion about reaching files on a
USB drive (FAT) from Disk BASIC: Disk BASIC thinks it is reading a floppy, but
it is really reading a directory chosen beforehand. It is a direction, not a
plan with dates. Nothing here is built yet. The Disk BASIC and CoCo 3 facts
below were checked in the ROMs themselves (see *Verified in the ROMs*).

![How the three options compare, and the short-term wins](directory-drives.svg)

The image is generated by `scripts/directory_drives_svg.py`; the same content
is in the tables below.

## The goal

An existing directory on a USB drive should just work as a CoCo disk: no
conversion, no sidecar files, no mangled names. Programs written for Disk
BASIC (DECB) should keep working unchanged, on the CoCo 1, 2 and 3 alike.
Anything new is a forward-looking addition: nothing that works today gets
deprecated.

It is not the only storage model the project will have. The native
filesystem in `PIZERO-70` to `PIZERO-74` (long names, hierarchy, a hypercall
ABI) is the opposite approach and still the right one for the Forth kernel,
which binds to the hypercall (`PIZERO-72`) directly. This proposal is about
what BASIC sees.

## What Disk BASIC gives us to work with

- **The disk.** 35 tracks of 18 sectors of 256 bytes: 161,280 bytes.
- **The directory track.** Track 17. Sector 2 is the FAT, sectors 3 to 11 the
  directory: 32-byte entries, 8 to a sector, 72 files at most. The rest of the
  disk is 68 granules of 9 sectors (2,304 bytes).
- **A directory entry.** Name (8 bytes), extension (3), file type (0 BASIC,
  1 data, 2 machine code, 3 text editor source), ASCII flag, first granule,
  bytes used in the last sector (2), 16 unused. A first byte of $00 marks a
  deleted entry, $FF an entry never used (the directory scan stops there).
- **The FAT.** One byte per granule: $FF free, $00 to $43 the next granule in
  the chain, $C0 to $C9 the last granule and how many of its sectors are used.
- **Limits.** 72 files a disk; 68 x 2,304 = 156,672 bytes a file.
- **File contents are the host file's bytes.** A tokenized `.BAS` or a
  LOADM-format `.BIN` is byte for byte what sits in the granules. No
  conversion is needed, which is what makes option 3 possible.
- **State.** DECB keeps a 74-byte copy of each drive's FAT in RAM at $0800 +
  74 x drive: 6 control bytes, then the 68 FAT bytes. Byte 0 counts the files
  open on that drive. The FAT read routine ($C79D) uses the copy while that
  count is nonzero, and otherwise re-reads track 17 sector 2 from the disk
  every time (and clears byte 1, the changed flag). The FAT is written back by
  $C71E. Verified.
- **DSKCON**, the sector routine, is reached through the vector at $C004, with
  its parameters at $EA to $F0 (operation, drive, track, sector, buffer
  pointer, status). Many programs call it directly.
- **ROM room.** DECB 1.1 is 8 KB at $C000 to $DFFF with 48 unused bytes
  ($D8D0 to $D8FF). On a CoCo 1 or 2 the cartridge window runs to $FEFF, so
  the 8 KB above DECB is free in a cartridge we emulate. On a CoCo 3 there is
  no room in that window: Super Extended BASIC's code fills $E000 to $FEFF,
  and $8000 to $BFFF is full too. Verified.
- **The CoCo 3 patches DECB.** At boot it copies its ROMs to RAM and, if
  `DK` is at $C000, patches Disk BASIC in place (routine $C322 in the CoCo 3
  ROM): for DECB 1.1 it writes 11 NOPs at $C8B4 and `JMP $E297` at $C0D9; for
  1.0 (told apart by the DSKCON vector at $C004) `JMP $E29D` at $C0C6.
  Verified.
- **Keywords.** The token space is finite and Super Extended BASIC uses much
  of it. Accepting more in existing keywords (quoted paths in `LOAD`, `OPEN`,
  `DIR`, `DRIVE`) is cheaper than adding keywords.
- **Filenames and default extensions.** The parser ($C938) starts with a
  blank name and the command's default extension, from a table at $C2A6:
  `BAS` (the LOAD and SAVE family), `DAT` (OPEN), `BIN` (LOADM and SAVEM), and
  blank (KILL, and COPY). A `.` or `/` clears the extension to spaces before
  reading up to 3 characters, so a trailing dot (`"LICENSE."`) gives a blank
  extension. A name over 8 characters, an extension over 3, or nothing before
  the dot is `?FN ERROR`. So Disk BASIC itself cannot make a name that is not
  8.3, and cannot even type one starting with a dot. Verified; which command
  uses which default is read from the callers, so the LOAD/SAVE and COPY
  attributions are inferred.

## Option 1: our own DOS

Replace DECB with our own cartridge ROM whose commands look like DECB's (same
keywords, same shapes) but work on long names and real directories. The ROM
is a thin 6809 shim; the filesystem work is C on the RP2350 behind the
hypercall. This is the existing `PIZERO-73` and `PIZERO-74` plan. DECB
behaviour is reproduced only where software needs it, through hooks.

- **For:** long names and real hierarchy; host limits instead of floppy
  limits; shares everything with the native/Forth side.
- **Against:** a program that goes below BASIC (DSKCON, `DSKI$`, a sector
  editor, its own loader) finds no disk, unless option 3 is built underneath
  anyway. Compatibility is only as good as our copy of DECB's syntax and side
  effects. The most work of the three. On a CoCo 3, a ROM that starts with
  `DK` gets Super Extended BASIC's patches written at DECB's fixed addresses
  ($C0D9, $C8B4), and one that does not is not treated as Disk BASIC at all,
  so the replacement has to plan for one or the other.

## Option 2: extended Disk BASIC

Keep DECB and add an extension in the spare cartridge space: existing
keywords also accept long quoted names and paths, which the extension hands
to the host through the hypercall before DECB's parser packs them into 8.3.

- **For:** everything DECB does keeps working, because DECB is still there.
  Long names reach the host without mangling.
- **Against:** DECB has 48 spare bytes, and on a CoCo 3 the whole $C000 to
  $FEFF window is taken (DECB and Super Extended BASIC), so an extension there
  needs memory outside the 64 KB map (another GIME block) or has to shrink to
  a stub that calls the host. Plain DECB commands still see floppy limits. Sector-level
  software works on `.DSK` images but needs option 3 to see a directory.

## Option 3: a virtual floppy built from a directory

DECB is not touched. The emulated floppy controller gets a new backend that
makes up a disk from a host directory instead of reading a `.DSK` file. The
controller that exists is a minimal WD279x: just the register behaviour DECB
uses (`lib/coco_machine/src/coco_machine.cpp:424`), plus sector writes and
what NitrOS-9 needed to boot.

**Only 8.3 names are seen.** A file whose name fits 8.3 (up to 8 characters,
up to 3 of extension, the extension optional) appears under exactly that
name. Everything else is ignored, and that includes any name starting with a
dot (it has no name part, so it is not 8.3) and every subdirectory (a
directory drive is flat, as a DECB disk is). 8.3 was the practical limit for twenty
years and is a clear limit for a small system; long names belong to OS-9 and
the native filesystem. This removes the naming problem entirely: no aliases,
no sidecars, and the DECB name *is* the host name, so SAVE, KILL and RENAME
map straight across. Lower-case host names count (repos are mostly lower
case); case is folded, and FAT cannot hold two names that differ only in case.

It also makes a repository a good home for a disk: `.git/`, `.gitignore` and
`CHANGELOG.md` drop out. `README.md` and `LICENSE` fit 8.3 and show up as
readable ASCII files, and that is wanted: a disk's `README.md` travels with it
and can be read on the CoCo. Anything meant to be read is fair game.

**Files without an extension** (`LICENSE`, `README`) are valid 8.3 and map
1:1: FAT and DECB both pad the extension with spaces. They come only from the
host, since every DECB save supplies an extension. They are not given one
(mapping them to `.TXT` would break the name identity). From BASIC, KILL and
COPY reach them as `"LICENSE"`, since their default extension is blank, and
every other command as `"LICENSE."`.

**Building the view.** At mount, give each file a run of granules and build
the FAT and the 9 directory sectors (about 2.5 KB). Data is not copied: a
68-entry map from granule to (host file, offset) serves data sectors from the
drive when they are read.

**Types without a sidecar.** The directory entry's type and ASCII flag matter:
DECB gives `?FM ERROR` when they do not suit the command, and LOAD of an ASCII
program re-tokenizes it. The content decides: a first byte of $FF is tokenized
BASIC, a valid $00 preamble is machine code, printable bytes are ASCII. The
extension breaks ties. When DECB saves, the type it writes picks the host
extension.

**Text is not translated at the disk level.** A directory drive serves every
file's bytes exactly as they are on the host, ASCII or not. Line endings and
character sets are the editor's and viewer's job (see *Text in the editor and
viewer* below), not the drive's. This keeps the drive simple (every file can
be served lazily, and nothing is ever lost in a translation) at one known cost:
Disk BASIC ends a line with CR ($0D) only, so an ASCII BASIC program saved on a
Mac with LF line endings will not LOAD until its line endings are CR.

**When the view may change.** It must hold still while DECB holds a FAT copy
with files open. Disk BASIC re-reads the FAT from the disk exactly when no
file is open on that drive (verified, above), so that read is the refresh
point: rebuild the view there, hold it until the next. This is the same hazard as
swapping a real floppy with a file open.

**No more disk full.** The emulator owns the disk, so free space is its to
give. Once a file is closed and written to the host, its granules go back to
the pool at the next refresh. What remains are limits on one operation, not
on the disk: one file up to 68 granules (156K), one view up to 72 entries, and
the files open at one moment fitting in 68 granules between them. A file too
big, or past the 72nd, is not shown, and the overlay says what was skipped
and why. One rule: if DECB could not hold it, it is not there.

**Writes are the hard part.** DECB writes data into free granules, then the
FAT, then a directory entry, and the emulator has to infer what was meant.
Writes to granules no file owns go to a scratch area; when the FAT or the
directory is written, compare it with the previous version: a new entry is a
new host file, a first byte of $00 is KILL (moved to a trash folder, not
deleted), a changed name is RENAME, a finished chain commits the file. Writes
to granules an existing file owns go straight through to it. QEMU's `vvfat`
does this for PC FAT and is fragile on writes; DECB is much simpler (one FAT,
a flat directory, one writer, a fixed write order), and the write order can
be traced on the board rather than guessed.

**What stays a `.DSK`.** Disks whose software depends on its own layout:
loaders that read fixed tracks and sectors, `DOS` boot disks (track 34),
copy-protected disks, and OS-9 disks. Directory drives are for files; `.DSK`
images are for software that knows where its bytes live.

**OS-9, for later.** Its disk format (RBF) is already hierarchical, with
names up to 29 characters, so it is closer to a host directory than DECB is.
NitrOS-9 is better served by a native device driver on the hypercall (the way
DriveWire's virtual drives work) than by a made-up disk.

## How they compare

| | 1 Our own DOS | 2 Extended DECB | 3 Virtual floppy |
|---|---|---|---|
| Existing BASIC programs | Partial: as far as the syntax matches | Strong: DECB is still there | Strong: DECB is not touched |
| Sector-level software | Weak: needs option 3 underneath | Partial: `.DSK` yes, directories need 3 | Strong: sectors are what it serves |
| Long file names | Strong: native | Strong: through the extension | Weak: 8.3 only, by design |
| A host directory just works | Strong: every file | Strong: every file, extended commands | Strong: 8.3 files, byte for byte |
| Capacity | Strong: host limits | Partial: DECB limits on plain commands | Partial: 156K a file, 72 a view, no disk full |
| 6809 ROM space needed | Partial: a new 8K ROM, assembler in the build | Weak: 48 bytes free in DECB; none on a CoCo 3 | Strong: none |
| Same on CoCo 1, 2 and 3 | Partial: must plan for CoCo 3 patching | Weak: the CoCo 3 window is full | Strong: below the ROM |
| Build effort | Weak: a DOS's BASIC side from scratch | Partial: hooks inside a full ROM | Partial: write inference, refresh rule |
| Shares work with native/Forth | Strong: same hypercall | Strong: same hypercall | Partial: shares the storage backend |

## Recommendation

Option 3 with the 8.3 rule as the compatibility floor: unmodified DECB sees
ordinary floppies that happen to be directories, and every program that works
today keeps working. The 8.3 rule means it needs no extension to be complete.
Option 2 becomes optional convenience on top later, not a requirement. Option
1's machinery (backend, hypercall) carries on as the native side for the Forth
kernel and OS-9, which is where long names belong.

## Short-term wins that pay off for all three

Each of these is useful on its own and is a piece of, or a help to, whichever
option is built. "Core" means the option is partly built out of it.

| Win | 1 | 2 | 3 |
|---|---|---|---|
| Host-file storage: directory drives on the SD card first (FatFs is already there), USB later (`PIZERO-70`, `PIZERO-78`) | core | core | core |
| DECB file rules as a host-tested library: 8.3 filter, type and ASCII sniffing, extension mapping | helps | core | core |
| The editor and viewer read any line ending and UTF-8 (next sections) | helps | helps | helps |
| Unpack a `.DSK` into a subdirectory of the same name and pack one back (next section) | helps | helps | core |
| ZIP import: open the zipped `.DSK` files most archives ship | helps | helps | helps |
| Check the DECB facts in the ROMs (done 2026-11-01, *Verified in the ROMs*) | helps | core | core |
| Overlay conveniences (next section) | helps | helps | helps |

The first win is the important one: option 3 can be built and proven on the
SD card before USB mass storage exists, since the backend is the only part
that changes.

Option-specific first steps, not shared: trace DECB's write order on the
board with the FDC trace build (option 3; that build crashes at boot today,
`PIZERO-198`), and the hypercall ABI (`PIZERO-72`, options 1 and 2 and Forth).

## Disk images and their directories

**The convention.** `GAME.DSK` unpacks into a subdirectory `GAME/` beside it,
holding one host file per DECB file, and `GAME/` packs back into `GAME.DSK`.
The pair is how a disk's contents are found, read, diffed and shared: the
directory works in a file browser, on GitHub and as a directory drive, and
the image works in every emulator. Names inside follow the 8.3 rule, which a
DECB disk satisfies by definition; the image's own name does not, since the
disk list already shows long names.

**What unpacking keeps and loses.** Every file comes through byte for byte,
with its type and ASCII flag recovered from the content and extension as in
option 3. What a directory cannot hold: a `DOS` boot track (track 34),
sectors outside any file's chain, deleted entries, and where each file sat on
the disk. So packing an unpacked disk gives the same files, not the same
image. Unpacking reports what it could not keep (the boot flag, sectors in
use that no file owns, broken FAT chains), and never deletes or replaces the
`.DSK`: for a disk that depends on its layout, the image stays the original.

**Packing** refuses a directory that does not fit (more than 72 files that
pass the 8.3 rule, or more than 68 granules between them) and says which
limit was hit. It writes to a temporary file and renames it, as the new-disk
command does (`PIZERO-193`), so a power cut never leaves a short image. If
`GAME.DSK` or `GAME/` already exists, it asks before replacing.

**When both exist,** neither is the master: they are two copies, and the one
edited last is newer. Keeping them in step automatically is out of scope;
unpack and pack are explicit commands in the disk list.

## ZIP import

Most `.DSK` files are distributed zipped, so ZIP support saves a trip to a
computer. Selecting a `.zip` in the disk list extracts it into a subdirectory
named after it, and the `.DSK` files inside then appear in the list like any
other. Extract-on-select is simpler than mounting straight from the archive,
and it leaves files that work everywhere. Read-only: making ZIPs is not
needed.

**The cost is memory, not code.** Stored and deflated entries cover nearly
every archive. An inflater such as `uzlib` or `tinf` is a few KB of code, but
deflate refers back up to 32 KB into its own output, and with a 128 KB CoCo 3
running the heap has about 9.7 KB free (`PIZERO-262`). Two ways round it: read
back-references from the file already written to the card, through a small
cache (slower, little RAM), or wait for PSRAM (`PIZERO-284`). The first works
on today's board and is the one to try.

## Text in the editor and viewer

Converting line endings belongs to the overlay's editor and viewer, not the
disk: whatever is read in is made right for editing, and a save writes the
file's native convention.

- **Reading:** CR, LF and CRLF all end a line. Today the editor only drops CR
  (`ted_load`, `src/text_edit.h:29`), so a CR-only file, which is what the
  CoCo writes, opens as one long line. That is the first thing to fix.
- **Saving:** the file's own convention, by precedent: a file that came in
  with CR goes back with CR, so a CoCo file stays loadable, and a file that
  came in with LF (the Mac) goes back with LF.
- **New files:** the CoCo's convention, CR alone.
- **First, the board's own parsers must accept CR.** Today every one of them
  splits lines on LF only: `settings.txt` and `NAME.TXT` through `f_gets`
  (`src/coco_boot.cpp:255`) and `settings.h:364` and `:421`, `autorun.txt`
  through `f_gets` (`src/coco_boot.cpp:668`), and `drives.txt` with
  `strchr(line, '\n')` (`src/coco_boot.cpp:861`). A CR-only file would read as
  one line, or as 96- and 260-byte pieces. A template the editor creates for a
  missing `settings.txt` or `autorun.txt` is a new file, so it would be CR and
  break unless this is fixed first. The board's own writers (`drives.txt`,
  the settings append in `settings.h:378`) should follow the same precedent
  rule.
- **On the Mac,** BBEdit, TextEdit and VS Code open CR-only files normally;
  `cat`, `grep` and `git diff` show one long line.
- **UTF-8:** shown folded to ASCII on the 6847 card (accents dropped, curly
  quotes straight, anything else a placeholder), but bytes the user did not
  touch are saved back unchanged, so editing one line of a file never
  destroys the Unicode elsewhere in it.

## Overlay conveniences from the same discussion

These help users now, whichever option ships.

- **Boot flag in the disk list.** `DOS` loads track 34 and checks for `OS` in
  its first two bytes, so the scan reads 2 bytes at offset 156,672 of each
  image and marks bootable disks. Pairs with `PIZERO-117` (offer to run
  what is on a disk).
- **FILES lists every text file**, decided by content rather than extension,
  so `LICENSE`, ASCII BASIC and assembler source open too. Today FILES is a
  fixed list of two (`src/disk_overlay.cpp:65`). Binary files are listed with
  an info line (size, type, load and exec address) instead of opening as text.
- **Directory drives are assigned as text.** The F12 disk list keeps working
  as it does today for `.DSK` images (`PIZERO-114`). Assigning a host
  directory to a drive is new, and it is done by editing a path in
  `drives.txt` from the FILES list, so the overlay does not grow a directory
  browser. Today `drives.txt` is written by the board ("N = path", "N ro =
  path", `src/coco_boot.cpp:735`), read back leniently, and rewritten whenever
  the assignments change, so hand edits have to be re-read on save and kept
  when the board rewrites the file.
- **Markdown read formatted**, the way `glow` shows it, with a key to switch
  into the editor. No Markdown renderer exists yet: it is `PIZERO-205` (the
  help reader, split off when the INFO page shipped as `PIZERO-156`), and the
  FILES list would use the same one. The 32 columns of the CoCo 2 card
  limit how much formatting fits.
- **DIR before it scrolls away.** A function key shows the current drive's
  listing in a scrollable popup (the overlay already reads RSDOS directories,
  `src/rsdos_dir.h`). Popping it up on DIR itself means trapping the known
  ROM entry; as an improvement it would default on, with plain DIR the other
  value. A DIR that pauses each screenful is the no-overlay alternative.
- **A hex editor** that overwrites in place (no insert or delete): 8 bytes a
  row, one 256-byte window plus a record of changed bytes, under 1 KB of RAM.
  On a `.DSK` it shows track and sector, on a `.BIN` its segments and load
  addresses. A mounted disk is ejected first, as rename does (`PIZERO-196`).
- **A detokenized listing** of a tokenized BASIC program, read-only.
- **Missing disk operations**, roughly by usefulness: delete (to a trash
  folder), copy, file info (size, type, boot flag, free granules), a `.DSK`
  consistency check (broken FAT chains), new text file and rename for the text
  list, make directory. New blank disk and rename exist (`PIZERO-193`,
  `PIZERO-196`).

## Relation to existing issues

- `PIZERO-74` records the August 2026 direction that BASIC's new commands be
  explicitly not DECB-compatible. This proposal points the other way for what
  BASIC sees; `PIZERO-74`'s description should be revisited once this
  direction is agreed.
- `PIZERO-70` (backend), `PIZERO-72` (hypercall) and `PIZERO-78` (USB mass
  storage) are shared. `PIZERO-79` (floppy support as a peripheral) still
  holds for layout-dependent `.DSK` images.
- The USB drive shares the PIO-USB host port through a hub: full speed, about
  1 MB a second, plenty for a CoCo.

## Verified in the ROMs

Checked 2026-11-01 by disassembling the ROM images in `~/github/cocotech/references`
(`disk11.rom`, Disk BASIC 1.1, MD5 `8cab28f4b7311b8df63c07bb3b59bfd5`) and the
CoCo 3 ROM (`coco3.rom`, MD5 `7233c6c429f3ce1c7392f28a933e0b6f`), with the
error tables in `bas12.rom` and `extbas11.rom`. Addresses are as mapped at run
time.

| Fact | Where | What the code does |
|---|---|---|
| FAT re-read | DECB $C79D | FAT copy at $0800 + 74 x drive. If byte 0 (open files) is nonzero, return; else clear byte 1, read track $11 sector 2 into $0600, copy 68 bytes in. |
| FAT write | DECB $C71E | Copy the 68 bytes to $0600 and write track $11 sector 2 (operation 3). Called after KILL frees a chain, and from two other paths ($C376, $C5B7). |
| Filename parser | DECB $C938 | Name field $094C to $0953 filled with spaces, extension $0954 to $0956 seeded with the default; `0:` prefix or `:0` suffix picks the drive; `.` or `/` blanks the extension; overflow or an empty name is error 31, `?FN`. |
| Default extensions | DECB $C2A6 | `BAS` $C2A6 (used at $CA33), blank $C2A9 (KILL $C6EF, COPY $D3B9 and $D3CB), `DAT` $C2AC (OPEN $C466), `BIN` $C2AF ($CFBB). |
| `?FN` is error 31 | `bas12.rom` $ABAF, `extbas11.rom`, DECB $C290 | 25 Color BASIC codes, then `UF` `NE`, then DECB's `BR DF OB WP FN FS AE FO SE`; FN is index 31, B = $3E. |
| DECB spare room | `disk11.rom` | One unused run: $D8D0 to $D8FF, 48 bytes of $00. |
| CoCo 3 room | `coco3.rom` | No unused run of 32 bytes or more in $8000 to $BFFF or $E000 to $FEFF. The internal $C000 to $DFFF is boot code, overwritten by Disk BASIC when a disk cartridge is present. |
| CoCo 3 patches DECB | CoCo 3 $C120, $C322 | If `DK` at $C000: DSKCON vector high byte $D6 (1.0) gets `JMP $E29D` at $C0C6; otherwise (1.1) 11 NOPs at $C8B4 and `JMP $E297` at $C0D9. |

What this changes: option 3's refresh rule rests on DECB's own behaviour, not
a guess; option 2 has no room on a CoCo 3 without leaving the 64 KB map, which
strengthens the recommendation; and names that are not 8.3 cannot be made by
Disk BASIC at all, so the 8.3 rule matches DECB exactly.
